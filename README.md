# Next Harness

**A guarded Next.js template for code that agents write.**

Your Claude Code or Codex agent is told where code belongs, stopped before it writes a file in the wrong
place, checked after every edit, and gated before it ends its turn.

## What it does

Agents write good code and bad shape. A `utils/` folder appears in every module, files grow past a
thousand lines, the same function is copied under three names, and `any` quiets the type checker.
Review catches some of it, late. This template checks the rules before the write instead.

- **One shape.** Routes in `src/app/`, features in `src/modules/<module>/`, cross-cutting code in
  `src/shared/`. Nothing else under `src/`, and nothing new at the repository root.
- **Limits.** 250 lines per file, 60 per page, 10 source files per folder. Folders named `utils`,
  `helpers`, `common` or `misc` are denied.
- **Boundaries.** A module is used only through `index.ts`, `server.ts` or an action file. `shared/`
  never imports a module. No import cycles.
- **No copies, no workarounds.** No duplicate exports, dead code or pasted blocks. No `any`, no
  `as never`, no `@ts-ignore`, no inline lint disables.
- **React and shadcn.** The React hook rules are errors. In a project with `components.json`, a raw
  `<button>` or `<input>` outside the generated `shared/ui/` is reported with the shadcn component to use.
- **A lock.** The agent cannot edit the harness, the hook settings or the tool configs. Only you can
  open the lock, with `pnpm harness:unlock` in your own terminal.

```text
src/
  app/                       routes and Next special files only; pages stay thin
  modules/<module>/
    index.ts                 client-safe public API: types, schemas, client components
    server.ts                server-only public API: queries, server components
    actions/<name>-action.ts Server Actions, first statement "use server"
    components/              feature UI
    server/                  internal queries and I/O
    domain/                  pure rules, no React or I/O, a test beside every file
    schemas.ts · types.ts
  shared/
    ui/                      shadcn primitives, generated by the shadcn CLI
    components/ · lib/ · hooks/
```

## How it works

The harness is a small TypeScript CLI in `tooling/harness/`. Claude Code and Codex call it from their
hooks, and Node 24 runs it directly with no build step.

| Moment           | What runs                                                                         | Takes    |
| ---------------- | --------------------------------------------------------------------------------- | -------- |
| Session start    | An index of every module's public exports, so the agent reuses before it writes   | one read |
| Before a write   | Guards: structure, `.env*` files, the lockfile, generated UI, the harness lock    | ms       |
| Before a command | Guards: force push, `rm` outside the checkout, destructive migrations, deploys    | ms       |
| After a write    | Fast gate: Prettier, syntax-level lint, path and content audit of that file       | ≈ 1–2 s  |
| After a command  | Audit of whatever the command created or changed                                  | ≈ 1 s    |
| Stop             | Done gate: types, typed lint, audit, boundaries, dead code, copies, related tests | seconds  |
| Pre-push and CI  | The full gate: all of the above on every file, all tests, `next build`, smoke     | minutes  |

Every denial says where the code belongs:

```text
src-shape: Put routes in src/app/, feature code in src/modules/<module>/, and cross-cutting
utilities in src/shared/lib/.
```

When the Done gate fails, the agent's turn does not end. It gets the findings and fixes them, at most
twice per prompt. After that it must report what still fails. Files changed in this turn block; older
problems elsewhere are only reported.

## Start a new project

You need Node 24 and pnpm.

```sh
git clone https://github.com/sladjanstojcic/next-harness.git my-product && cd my-product
pnpm install --frozen-lockfile
pnpm run prepare                     # enables the pre-push hook
pnpm rename --name my-product --port 3100 --title "My Product"
pnpm exec playwright install chromium
pnpm dev
```

No secrets are needed. `.env.example` documents the starting environment.

## Add it to an existing project

The harness is one folder, `tooling/harness/`, added with `git subtree`. For a single Next.js app at the
repository root:

```sh
git subtree add --prefix=tooling/harness https://github.com/sladjanstojcic/next-harness.git harness --squash
node tooling/harness/cli.ts init --starter   # first run: lists tooling/harness as a workspace package, then stops
pnpm install
node tooling/harness/cli.ts init --starter   # second run: writes the wiring, prints the next steps
```

Then do the printed steps in order and finish with `pnpm run check`. Init installs nothing itself and
never replaces a config you already have.

Other project kinds add one file, `harness.config.ts`, that says which folder has which shape. Each
guide has numbered steps that were run on a fresh project of that kind, from an empty folder:

| Your project                 | Guide                                |
| ---------------------------- | ------------------------------------ |
| Existing Next.js app         | [docs/next-app.md](docs/next-app.md) |
| Turborepo or other monorepo  | [docs/monorepo.md](docs/monorepo.md) |
| A new shared package         | [docs/packages.md](docs/packages.md) |
| Electron app (electron-vite) | [docs/electron.md](docs/electron.md) |
| Vite single-page React app   | [docs/vite.md](docs/vite.md)         |
| Makerkit project             | [docs/makerkit.md](docs/makerkit.md) |

The Makerkit page has no numbered walkthrough yet.

A project with old code gets a legacy list: old files are tolerated, new files are held to every rule,
an old file you touch must clear its type, lint, format and import findings, and the list may only
shrink. `node tooling/harness/cli.ts legacy prune` takes the files with no finding left off it.

## Let the agent in

- **Claude Code:** accept the workspace trust dialog. `.claude/settings.json` wires the hooks.
- **Codex:** trust the project's `.codex/` configuration and review the hooks in `/hooks`. In a linked
  git worktree Codex skips project hooks, so run `pnpm codex:hooks` once to install them at user level.

[AGENTS.md](AGENTS.md) is what the agent reads in this template: the shape, where each kind of code
goes and when the checks run. Init does not write one into an adopting project; copy the sections that
apply.

## Daily use

```sh
pnpm check                 # the full gate; what pre-push and CI run
pnpm run audit             # the harness audit alone
pnpm harness:blocks        # every denial and block, per rule
pnpm harness:unlock        # open the harness for four hours; pnpm harness:lock closes it
```

You give the agent a task. It is stopped before a write in the wrong place and told where the code
belongs. When it says it is done, the Done gate sends it back with the findings. You push, and the
pre-push hook runs the full gate. Now and then read `pnpm harness:blocks`: a rule that mostly blocks
good code is a bug in the harness, and you can mark such a block false.

## Update the harness

```sh
git subtree pull --prefix=tooling/harness https://github.com/sladjanstojcic/next-harness.git harness --squash
node tooling/harness/cli.ts init    # adds wiring the new version needs; keeps what is already there
```

Run both in your own terminal, since `tooling/harness/` is locked for agents.
